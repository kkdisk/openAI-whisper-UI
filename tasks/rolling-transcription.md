## 1. 背景與目標

使用者一份 2:24:28 的錄音超過 120 分鐘上限，被 `duration_limit` 拒絕。工作區已將上限調為 180 分鐘，修改了以下四處：

- app/config.py
- app/static/index.html
- SPEC.md:75
- README.md:83

這次修改後，tests/test_transcriber.py、test_api.py、test_frontend.py 的結果為 29 passed、1 skipped。

時長上限是資源保護，不是模型限制。Whisper 本來就以 30 秒視窗依序推論；真正隨時長線性成長的是「整段解碼後一次算特徵」的記憶體（見第 2 節）。

### 目標

1. 程序峰值 RAM 與音檔總長脫鉤，只由區塊長度決定上界。
2. 辨識品質與現行整段路徑相當，區塊邊界不漏句、不重複提交、時間軸不錯位。
3. 保留以下既有行為：
   - 逐段保存
   - 暫停／繼續
   - 取消
   - GPU 首段前回退
   - 人工修訂
   - 匯出格式
4. 產生可重建的處理邊界，作為 H50 斷點續跑的前置。本計畫不實作續跑。

### 非目標

本計畫不處理以下項目：

- 斷點續跑（H50）
- 說話者分離（M8／M9）
- 推論加速或 BatchedInferencePipeline
- 即時麥克風串流
- 改變預設模型或辨識參數

## 2. 現況分析

以下依據 app/transcriber.py 與 faster-whisper 1.2.1 原始碼（.venv/Lib/site-packages/faster_whisper/）整理。

### 2.1 記憶體路徑

| 步驟 | 位置 | 2.5 小時（144M 樣本）的暫時用量 |
|---|---|---|
| 整檔解碼：int16 片段＋合併＋float32＋除法暫存 | transcriber.py:26 `decode_media` | 約 1.4 GB，返回後常駐約 576 MB |
| VAD 合併語音段：`collect_chunks` 加 `np.concatenate` | transcribe.py:891 | 最多約 1.1 GB |
| 整段 STFT：rfft 產生 complex64，約 90 萬幀 × 201 | feature_extractor.py、transcribe.py:916 | 約 1.45 GB |
| 取 abs 再平方 | 同上 | 約 0.7 GB × 2 |
| mel 特徵常駐：80 mel；turbo 為 128 mel | 同上 | 約 0.29～0.46 GB |

上表是依程式碼推算的數字，沒有實測。各步驟不完全重疊。

把模型（small 約 0.8 GB）和資料路徑（約 25～30 MB／分鐘）加起來，可粗估程序峰值：

| 音軌長度 | 推算峰值 |
|---|---|
| 60 分 | 約 2.5 GB |
| 108 分（R01） | 約 3.5～4 GB |
| 150 分 | 約 4.5～5.5 GB |
| 180 分 | 約 5.5～6.2 GB |
| 360 分 | 約 10～11.5 GB |

SPEC 的初始目標是 8 GiB，依此推算約在 4.5 小時附近超過。R01 的 108 分鐘曾以 small／CPU 完成，耗時 57 分 37 秒，但當時未量測峰值 RAM。

### 2.2 其他與時長相關的限制

| 項目 | 現況 | 對長檔的影響 |
|---|---|---|
| 上傳上限 4 GiB | config.py | 純音檔沒有問題；高位元率的長 MP4 可能超過，建議先轉 M4A |
| 上傳總時限 3600 秒 | config.py `upload_total_sec` | 本機上傳不受影響 |
| 片段常駐主程序記憶體 | jobs.py `self.segments` | 12 小時約 3～4 萬段，記憶體可接受 |
| 前端渲染全部片段 | app.js `append` | 3 萬段以上的 DOM 數量未驗證，可能卡頓（見第 7 節風險） |
| 狀態只能往前 | jobs.py `monitor`：VALIDATING → LOADING_MODEL → DECODING → TRANSCRIBING | 分段後不能每塊都回報一次 decoding |

### 2.3 提示詞行為（讀原始碼所得，須實驗確認）

faster-whisper 的 `get_prompt`（transcribe.py:1550）只保留前文最後 223 個 token，也就是 `max_length // 2 - 1`。初始提示（引導句＋專有名詞）是放在前文開頭的。這帶來兩個結果：

- 現行整段路徑中，初始提示在辨識幾個視窗後就會被新文字擠出。
- 關閉「參考前文」時，初始提示只作用於第一個視窗。

也就是說，現在的專有名詞提示實際上主要只影響錄音開頭。分段後每塊都會重新帶入提示，可能改善術語辨識，也可能改變重複或幻覺的行為。這點必須在 A/B 比較中觀察，不能預設是改善。

## 3. 設計

### 3.1 流程

```
PyAV 串流解碼（只保留「目前區塊＋邊界搜尋視窗」的樣本）
  → 累積到 block_sec
  → 在 [block_sec − search_sec, block_sec] 內找非語音間隙作為切點
  → model.transcribe(本塊, **options)
  → 片段時間戳加上本塊在原檔中的偏移；segment_id 全域連號；逐段 emit
  → 切點之後的殘餘樣本移到下一塊開頭
  → 重複，直到檔案結束（最後一塊不再找切點）
```

### 3.2 串流解碼

1. 新增產生器 `iter_audio_blocks(path, block_sec, search_sec, max_duration_sec, cancelled)`，逐塊產出 `(offset_samples, float32 ndarray)`。
2. 沿用 `decode_media` 的檢查：
   - 沒有音軌
   - 空音訊
   - 宣告時長或累計樣本數超過上限
   - 解碼失敗
   - 取消
3. 錯誤碼與訊息保持一致。
4. `AudioResampler` 只在檔案結尾 flush，不能每塊都 flush，否則會漏掉樣本。單元測試須驗證兩件事：
   - 所有區塊依序串接後，與 `decode_media` 的輸出逐樣本相同。
   - 總樣本數相同。
5. `decode_media` 保留，供整段模式、benchmark 腳本及短檔使用。

### 3.3 邊界選擇

1. 在搜尋視窗內用已載入的 Silero VAD（`get_speech_timestamps`）找非語音間隙。
2. 邊界搜尋使用專用的 `VadOptions`，與辨識用的 VAD 設定分開：
   - faster-whisper 的辨識預設是 `min_silence_duration_ms=2000`、`speech_pad_ms=400`。在這組設定下，0.5 秒的靜音會被併入語音；即使把最短靜音改成 300 ms，兩側各 400 ms 的 padding 仍會把間隙填滿。照原本的寫法實作，會經常落入強制切點。
   - 邊界專用的參數建議初值為：`min_silence_duration_ms` 約 150～200、`speech_pad_ms=0`、`threshold` 沿用 0.5。實際數值由 T100.1 的測試與 T100.3 的實檔數據定案。
   - 間隙定義為搜尋視窗內語音區段之間的空白，也包含視窗兩端到語音之間的空白。
   - 辨識階段仍沿用既有的 `vad_filter` 預設，不受邊界參數影響。
3. 取最長且至少 `min_gap_sec`（建議 0.3 秒）的間隙，切在間隙中點。
4. 找不到間隙（持續說話）時，切在視窗內 20 ms 能量最低處，並在 `meta.warnings` 記錄 `boundary_forced@<秒數>`。這筆紀錄只有時間，不含逐字稿內容。
4. 第一版不做區塊重疊。原因如下：
   - 重疊需要去重，而專案規則禁止以相同文字去重，以免刪掉真實的重複發言。
   - 以時間戳去重另需實驗。
5. 如果 R1 實驗顯示強制切點有明顯漏字，再評估「重疊＋時間戳去重」，列為 T100.3 的分支實驗。

### 3.4 每塊辨識

- **VAD**：每塊各自呼叫 `model.transcribe(block, **options)`，`vad_filter` 照舊。
- **時間戳**：faster-whisper 已把 VAD 後的時間還原為塊內時間，再加上 `offset_sec` 即可。越界依下列規則處理，任何情況都不刪除文字（見下方「時間戳越界規則」）。
- **連號**：`segment_id` 由 `_transcribe` 全域累加，jobs.py `monitor` 的連號檢查不變。
- **語言**：
  - zh／en：固定。
  - auto：鎖定時機延後到「第一個含有效語音的區塊」，詳見下方「auto 語言鎖定」。偵測結果記入 meta。
  - mixed：每塊 `multilingual=True`，照舊。

**時間戳越界規則**

專案既有做法（validation.md:210）是：時間戳超出音軌時保留原文，不刪除也不裁切。formatter.py:92-100 遇到非有限值或 `start > end` 會拒絕整份 SRT。依此訂定：

| 情況 | 處理 |
|---|---|
| 非最後一塊，`end_sec` 超過下一塊起點 | `end_sec` 改為下一塊起點 |
| 非最後一塊，`start_sec` 也超過下一塊起點（例：塊長 600 秒，片段 601～603 秒） | `start_sec` 與 `end_sec` 都改為下一塊起點，成為零長度片段；這樣 `start ≤ end` 仍成立，SRT 可匯出 |
| 最後一塊越過音軌結尾 | 不裁切，與整段路徑的行為相同 |
| 非有限數值（NaN、inf） | 不修改，與整段路徑相同；記錄 warning |
| `start_sec` 小於本塊起點 | 改為本塊起點 |

- 每次調整都在 `meta.warnings` 記錄 `timestamp_adjusted@<segment_id>:<原始塊內起訖秒數>`，只含數值，不含逐字稿內容。
- 文字一律保留。
- 測試涵蓋：雙端越界、單端越界、零長度、非有限值、最後一塊越界。每項都要確認 SRT 仍能匯出，或得到與整段路徑相同的錯誤。

**auto 語言鎖定**

現行整段路徑先做 VAD，再從保留下來的語音偵測語言。分段路徑的第一塊可能整塊都是靜音，若直接鎖定這一塊的 `info.language`，就會把沒有語音依據的判斷套用到全文。規則如下：

1. 尚未鎖定前，每塊都用 `language=None` 自行偵測。
2. 某一塊的 `info.duration_after_vad` 達到 `language_lock_min_speech_sec`（建議 2 秒，實驗定案）時，鎖定該塊的偵測結果，給後續各塊使用。
3. 全檔都沒有達到門檻時，維持逐塊偵測，結果與整段路徑一樣不可靠；在 meta 記錄「未鎖定」。
4. 測試涵蓋：
   - 第一整塊靜音、第二塊才開始中文
   - 全檔靜音
   - 第一塊只有短促雜音
- **前文接續**（`condition_on_previous_text=True` 時）：
  - 下一塊的 `initial_prompt` 由「引導句＋術語＋上一塊尾端原文」組成。
  - 總 token 數必須 ≤ 223，以免 `get_prompt` 從開頭截掉術語。
  - 尾端原文的預算 = 223 − 引導與術語 token − 安全餘量，且不超過設定值 `prev_context_tokens`。
- **不接續前文**（`condition_on_previous_text=False` 時）：每塊只帶「引導句＋術語」，與現行第一個視窗相同。
- **後處理**：繁體轉換 `convert_text`、`raw_text` 保存方式不變。

### 3.5 控制、狀態與 GPU

- **暫停**：沿用 `controlled_segments`。在每塊開始解碼前及開始推論前，再各加一個 `checkpoint()`；區塊之間是乾淨的暫停點。
- **取消**：解碼迴圈中與區塊之間都檢查取消。
- **狀態**：第一塊之前回報一次 `decoding`，開始第一塊推論時回報 `transcribing`。後續區塊的解碼在 transcribing 期間靜默進行，不違反狀態只能往前的規則。暫停按鈕的可用時機不變。
- **GPU 回退**：判斷條件統一為「第一個正式片段提交之前」，也就是 jobs.py 現行的 `meta.segment_count == 0`，與失敗發生在第幾塊無關。
  - 例：第一塊只有靜音、沒有輸出，第二塊發生 CUDA 故障。此時仍未提交任何片段，auto 模式照常換用 CPU 工作程序從頭重跑。
  - 已提交過片段之後才發生故障，保留原稿與人工修訂，不自動重跑。
  - 測試涵蓋：首塊無輸出且第二塊 CUDA 失敗（應回退）、首塊已有片段且第二塊失敗（不回退）。

### 3.6 進度與 metadata

**`info` 事件**

1. `duration_sec` 先填容器宣告的時長：優先用 `stream.duration × time_base`，沒有時用 `container.duration / AV_TIME_BASE`。都沒有時填 `None`；前端對空值已顯示「估算中」。
2. 辨識結束前，再送一次 `info`，填入實際解碼的時長，`versions` 與 `model_revision` 一併重送。

**`JobMeta` 新增欄位**

新欄位都有預設值，舊任務讀取時視為整段模式，`schema_version` 維持 1。

| 欄位 | 型別與預設 |
|---|---|
| `segmentation` | `"whole" \| "rolling"`，預設 `"whole"` |
| `block_sec` | `float \| None` |
| `boundaries_sec` | `list[float]`，各區塊在原檔中的起點 |
| `detected_language` | `str \| None` |

`boundaries_sec` 供以下用途使用：

- 品質檢查
- H40 局部重辨識
- H50 checkpoint

**匯出**

TXT 與 MD 的標頭比照前文設定，記錄分段模式與區塊長度。

T100.1 的單元測試涵蓋：

- 串接後與整檔解碼逐樣本相同
- 有靜音與無靜音的切點
- 0.3、0.5、1 秒的間隙，分別位於搜尋視窗開頭、中間、結尾；確認在邊界專用 VAD 參數下都能找到，在辨識預設參數下的結果另外記錄對照
- 強制切點產生 warning
- 最後一塊長度很短
- 時長上限
- 取消

T100.2 的產出：

- 每組都在獨立子程序中執行，避免峰值 RAM 互相污染。
- 每組輸出原文 JSONL、切點清單、峰值 RAM、耗時與 manifest（含來源 SHA-256、模型 revision、套件版本）。
- 「邊界對照報告」：每個切點前後 ±30 秒的整段稿與分段稿並列，供人工回聽。
- 整體字數差異及差異最大的區間。

T100.3m 的方法：

1. 只比較不同內容的檔案，無法證明記憶體與總長脫鉤：線性成長可能被模型的固定用量掩蓋，語音比例不同也可能讓正確的實作超標。因此改用同一段素材。
2. 從同一段約 36 分鐘的素材，以首尾串接做出 1×、2×、4× 三種長度（36、72、144 分鐘）。串接結果只存在 temp/，不提交。
3. block_sec、模型、執行緒、裝置與其他參數全部固定。
4. 每組在獨立子程序中執行，記錄：
   - 程序峰值（`PeakWorkingSetSize`）
   - 每塊完成時的 `WorkingSetSize`，形成逐塊記憶體曲線
5. 同組的整段路徑也跑 1×、2×、4×，作為「會線性成長」的對照組。
6. 工作程序的 RAM 與主程序的 RAM 分開記錄。主程序會累積片段、SSE 狀態與修訂；它的成長是預期中的線性小量，在 R3 以實際 UI 流程另外量測，不併入工作程序的脫鉤判定。

## 6. 驗收標準

以下是建議門檻，須使用者確認後才定案。

| 面向 | 標準 |
|---|---|
| 記憶體 | 依 T100.3m 同素材 1×／2×／4× 實驗判定，三項都要符合：① 分段模式工作程序的峰值，4× 比 1× 增加不超過 200 MB；② 逐塊記憶體曲線在第二塊之後沒有持續上升的趨勢，以逐塊工作集的線性迴歸斜率判讀，門檻由實驗定案；③ small／CPU／block 600 秒時峰值 ≤ 3 GB。整段路徑對照組應呈現明顯的線性成長，用來確認量測方法確實看得出差異。主程序 RAM 另行記錄，不列入這項判定 |
| 耗時 | 總耗時不超過整段路徑的 110% |
| 完整性 | 最後一段的 end_sec 與整段路徑的結尾差距 ≤ 30 秒；全文字數差異不超過 T100.3 量到的整段基準雜訊的兩倍 |
| 邊界 | 每個切點都經人工回聽，沒有確認的漏句或重複句；強制切點逐一列出並確認 |
| 品質 | 術語、語言判斷、重複片段數與整段路徑並列比較，由使用者判定是否可接受；不以字數相近代替品質 |
| 行為 | 第 4 節各項維持；完整 pytest、Node 前端測試、ruff 通過 |

所有量測都記錄 Windows 版本、套件版本、電源模式與背景負載，沿用 SPEC 的量測規則。沒有量測到的項目標示「未記錄」，不補造數據。

## 7. 風險

| 風險 | 影響 | 處理 |
|---|---|---|
| 切點落在語句中間 | 漏字、斷句 | 優先切在靜音處；強制切點記錄 warning 並人工回聽；必要時評估重疊方案 |
| 邊界 VAD 參數不當 | 若沿用辨識預設，短間隙會被合併，大量落入強制切點 | 邊界使用專用參數；T100.1 測試不同長度與位置的間隙；T100.3 統計強制切點的比例 |
| 時間戳越界 | 起訖倒置使整份 SRT 無法匯出，或與下一塊重疊 | 依 3.4 的越界規則處理：不刪文字、記錄 warning，最後一塊與整段路徑行為一致 |
| 前文中斷 | 跨區塊用詞不一致 | 下一塊帶入上一塊尾端原文；以 token 預算保護術語不被截掉 |
| 每塊重新帶入術語提示 | 術語可能變好，也可能誘發重複或幻覺 | A/B 比較重複片段數與術語命中，提示策略由數據決定 |
| auto 語言逐塊偵測 | 中途改判語言；或首塊靜音時鎖定錯誤語言 | 在第一個有效語音量達門檻的區塊才鎖定；mixed 模式維持逐窗偵測 |
| 區塊開頭的 VAD 邊緣效應 | 開頭第一個字被吃掉 | 切在間隙中點，兩側保留靜音；單元測試及回聽檢查 |
| 容器沒有宣告時長 | 進度與 ETA 無法顯示，無法預先拒絕超長檔 | 顯示「估算中」；串流計數超過上限即中止 |
| 超長檔處理時間 | 12 小時錄音以 CPU small 約需 6～7 小時，期間睡眠或重啟無法接續 | UI 提示預估時間；接續功能留待 H50；建議 GPU 或插電執行 |
| 前端渲染數萬段 | 卡頓 | T100.9 先量測，必要時另行規劃 |
| 改動破壞暫停與取消時序 | 控制失效 | 沿用 CooperativeControl；tests/test_pause.py 以兩種模式重跑 |
